# 底盘控制故障排查

状态：`active`（导航见 `README.md`）

本文用于排查以下典型问题：

- `MOVE` 无法前进或后退
- `ROTATE` 可以执行，但其他运动不执行
- `/chassis/command` 发出后机器人无动作
- `GOTO_GOAL`、`PATROL_GOALS` 无法执行

本文同时覆盖：

- 总控单 topic 控制链路
- 协议桥接链路
- 机器人任务状态与现场执行状态

## 1. 核心思路

排查这类问题，不要只看“机器人有没有动”，而要按下面 4 层逐步定位：

1. 命令有没有发到桥接节点
2. 桥接节点有没有成功转成协议 HTTP 请求
3. 机器人有没有接收并开始执行 mission/task
4. 机器人执行层为什么没有按预期运动

也就是：

```text
命令发布
  -> /chassis/command_result
  -> /protocol/mission_state
  -> /protocol/task_state
  -> /protocol/robot_status
  -> /protocol/robot_alarm
```

## 2. 先打开哪些观察窗口

至少打开以下 5 个终端观察：

```bash
ros2 topic echo /chassis/command_result
```

```bash
ros2 topic echo /protocol/mission_state --full-length
```

```bash
ros2 topic echo /protocol/task_state --full-length
```

```bash
ros2 topic echo /protocol/robot_status --full-length
```

```bash
ros2 topic echo /protocol/robot_alarm --full-length
```

## 3. 先确认桥接链路是否存在

### 3.1 确认桥接节点已启动

```bash
ros2 node list
```

应至少看到：

- `/protocol_command_bridge`

如果没有，先启动：

```bash
cd /home/raybot/raybot_chassis_ws
source /opt/ros/humble/setup.bash
source install/setup.bash
ros2 launch chassis_move protocol_command_bridge.launch.py
```

### 3.2 确认 `/chassis/command` 确实有订阅者

```bash
ros2 topic info /chassis/command -v
```

应至少满足：

- topic 存在
- 类型是 `raybot_chassis_msgs/msg/ChassisCommand`
- 至少有一个 subscriber

如果执行命令时看到：

```text
Waiting for at least 1 matching subscription(s)...
```

说明当前没有节点在订阅 `/chassis/command`。

优先排查：

- `protocol_command_bridge` 是否已启动
- 当前终端是否已经 `source /opt/ros/humble/setup.bash`
- 当前终端是否已经 `source install/setup.bash`

## 4. 标准排查顺序

每次发一条测试命令后，都按下面顺序看。

### 第一步：看 `/chassis/command_result`

这是第一层判断口。

#### 情况 A：完全没有新消息

说明命令没有到桥接节点。

重点排查：

- `/chassis/command` 是否有 subscriber
- 桥接节点是否在运行
- 命令是否发到了错误 topic
- 当前终端是否 `source` 正确

#### 情况 B：有消息，但 `ok=false`

说明桥接层处理失败。

重点看：

- `error`
- `request`
- `request_raw`

常见原因：

- 参数缺失
- `command_type` 不支持
- 机器人 HTTP 地址不可达
- 机器人接口返回错误码

#### 情况 C：有消息，且 `ok=true`

说明桥接层已成功把命令转成协议请求并发送给机器人。

接下来继续看机器人执行层。

## 5. 第二步：看 `/protocol/mission_state`

### 情况 A：完全没有 mission 状态

说明桥接层调用成功，但机器人没有正常回调任务状态。

重点排查：

- `protocol_bringup` 是否正常启动
- 香橙派回调地址是否正确
- 机器人是否能访问香橙派回调服务

### 情况 B：出现了 mission 状态

继续重点看：

- `mission_state`
- 是否从 `STARTING` 进入 `RUNNING`
- 是否进入 `FAILED`、`CANCELED`、`INTERRUPTED`

如果任务很快失败，问题通常已经进入机器人执行层或任务条件层。

## 6. 第三步：看 `/protocol/task_state`

这里用来确认机器人到底在执行哪个子任务。

协议标准字段名是：

- `task_cmd`
- `task_state`

重点关注：

- `task_cmd=move`
- `task_cmd=head`
- `task_cmd=goto`
- `task_state=STARTING/RUNNING/FAILED/SUCCEED`

### 常见判读

#### 1. `ROTATE` 能动

应看到：

- `task_cmd=head`

#### 2. `MOVE` 应能动

应看到：

- `task_cmd=move`

如果桥接是 `ok=true`，但没有 `task_cmd=move`，说明机器人没有进入对应任务执行流程。

#### 3. `GOTO_GOAL` / `GO_HOME` / `PATROL_GOALS`

应看到：

- `task_cmd=goto`

如果没有 `goto`，说明任务没有真正开始导航。

## 7. 第四步：看 `/protocol/robot_status`

当任务已经开始时，这里用来判断“机器人有没有实际运动”。

### 7.1 对 `MOVE`

重点看：

- `pose_msg.px`
- `pose_msg.py`

前进/后退时应出现位置变化。

如果：

- `/protocol/task_state` 里有 `task_cmd=move`
- 但 `pose_msg.px/py` 基本不变

说明命令已经到机器人执行层，但机器人没有真正运动。

### 7.2 对 `ROTATE`

重点看：

- `pose_msg.pt`

如果旋转成功，应看到朝向变化。

### 7.3 对 `GOTO_GOAL`

重点看：

- `pose_msg.px/py/pt`
- `status_msg.lost`
- `status_msg.stuck`
- `pose_msg.score`

如果导航不动或走偏，要结合状态判断是否迷路、卡住或异常。

## 8. 第五步：看 `/protocol/robot_alarm`

如果任务已经到机器人执行层，但没有实际按预期运动，报警 topic 很关键。

重点看：

- `device`
- `code`
- `level`
- `error_msg`
- `error_handling`

当出现：

- 安全传感器报警
- 驱动报警
- 定位异常
- 导航异常

时，机器人可能会：

- 接任务成功
- mission/task 也有状态
- 但现场不运动或立即停住

## 9. 典型问题定位

### 9.1 `ROTATE` 可以，其他运动不行

优先级最高的判断：

1. `ROTATE` 只依赖 `head`，不依赖地图和目标点
2. `GOTO_GOAL`、`PATROL_GOALS` 依赖地图、目标点、导航状态
3. `MOVE` 前后直线动作虽然不依赖目标点，但可能受机器人当前模式、安全状态、底盘执行限制影响

应重点看：

- `/protocol/task_state` 中是否真的出现 `task_cmd=move` 或 `task_cmd=goto`
- `/protocol/robot_alarm` 是否有报警
- `/protocol/robot_status.status_msg` 中是否有 `lost/stuck/estop`

### 9.2 后退不能动

代码层面当前负距离会原样下发为：

- `{"cmd":"move","distance":-300,"speed":150}`

因此如果前进能动、后退不能动，**优先怀疑机器人本体执行限制或底盘固件行为**，而不是桥接代码吞掉了负号。

建议重点看：

- `/chassis/command_result` 是否 `ok=true`
- `/protocol/task_state` 是否有 `task_cmd=move`
- `/protocol/mission_state` 是否进入 `FAILED`
- `/protocol/robot_alarm` 是否有驱动/安全相关报警

### 9.3 `GOTO_GOAL` / `PATROL_GOALS` 不动

优先检查：

- 当前地图是否正确
- 目标点名称是否存在且大小写一致
- `/protocol/task_state` 是否出现 `task_cmd=goto`
- `/protocol/robot_status.status_msg.lost` 是否为 `true`
- `/protocol/robot_status.status_msg.stuck` 是否为 `true`

## 10. 建议的最小测试顺序

现场联调时，不要一上来就测复杂导航，建议按下面顺序：

1. 切模式
```bash
ros2 run raybot_chassis_master chassis_master_cli -- set-mode AUTOMATIC
```

2. 旋转
```bash
ros2 run raybot_chassis_master chassis_master_cli -- \
  rotate --angle-deg 10 --speed-deg-s 10
```

3. 前进
```bash
ros2 run raybot_chassis_master chassis_master_cli -- \
  move --distance-mm 300 --speed-mm-s 150
```

4. 后退
```bash
ros2 run raybot_chassis_master chassis_master_cli -- \
  move --distance-mm -300 --speed-mm-s 150
```

5. 到目标点
```bash
ros2 run raybot_chassis_master chassis_master_cli -- goto-goal --goal A
```

这样最容易区分：

- 是桥接链路问题
- 是底盘动作执行问题
- 还是导航/地图问题

## 11. 最终定位口径

可以按下面口径给结论：

### 桥接层问题

满足任一条即可：

- `/chassis/command_result` 没消息
- `/chassis/command_result` 中 `ok=false`

### 机器人任务层问题

满足任一条即可：

- `ok=true`，但没有 `/protocol/mission_state`
- 有 mission，但没有正确的 `task_cmd`

### 机器人执行层问题

满足任一条即可：

- 有正确 `task_cmd`
- 任务进入 `RUNNING`
- 但 `robot_status` 位姿/朝向没有相应变化
- 或报警 topic 出现异常

### 地图/导航条件问题

更偏向以下情况：

- `ROTATE` 正常
- `MOVE` 可能正常或异常
- `GOTO_GOAL` / `PATROL_GOALS` 异常
- 同时伴随目标点不存在、地图错误、定位丢失、卡住等现象

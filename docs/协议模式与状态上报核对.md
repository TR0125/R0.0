# 协议模式与状态上报核对

> 状态：`archive`
> 
> 主入口请优先使用：`对外接口文档.md`（模式与状态判据章节）。

本文基于 [调度系统与机器人通信协议20260507-1.pdf](/home/raybot/raybot_chassis_ws/docs/调度系统与机器人通信协议20260507-1.pdf) 与当前 `raybot_chassis_ws` 实现进行核对，回答两个问题：

1. 香橙派当前控制底盘，是否应归类为 `AUTOMATIC`，而不是 `SEMIAUTOMATIC`
2. 协议中的机器人状态上报，在当前代码里是否有对应体现，字段名称是否发生变化

## 1. 结论

### 1.1 模式归类结论

如果香橙派当前扮演的是“上层调度/总控系统”的角色，通过协议向机器人下发 `mission`、模式切换、停止、状态请求等指令，并由机器人按任务自主执行，那么**更符合协议中 `AUTOMATIC`（调度模式）的定义**。

`SEMIAUTOMATIC`（就绪模式）更适合以下场景：

- 机器人仍可接收调度任务，但允许人工做部分操作
- 人工远程触发 `idle`、充电等动作后，机器人处于等待或半接管状态
- 机器人完成特定人工介入流程后，再回到调度模式

因此，如果现场实际运行方式是：

- 香橙派统一发任务
- 机器人自主导航和执行
- 人工不持续介入任务过程

那么文档和联调流程中把机器人切到 `SEMIAUTOMATIC` 只能算“当前现场可用配置”，**从协议语义上更推荐使用 `AUTOMATIC` 作为标准归类**。

### 1.2 状态上报结论

协议里的状态上报在当前代码中**基本都有对应**，主要方式是：

- `ProtocolGatewayNode` 接收机器人 HTTP 回调
- 将原始 JSON 直接转发到 `/protocol/*` ROS topic

也就是说，当前实现对状态上报的总体策略是：

- **路径有映射**
- **消息原文基本透传**
- **只有少量本地抽象层字段名做了包装**

## 2. 协议中的模式定义

根据 PDF 第二章“机器人模式”：

- `AUTOMATIC`：调度模式，可接收调度任务，机器人运行完全由调度系统控制
- `SEMIAUTOMATIC`：就绪模式，可接收调度任务，但允许人工进行部分操作
- `MANUAL`：手操模式，不可接收调度任务
- `SERVICE`：调试模式，不可接收调度任务

当前代码和文档中有多处示例仍然使用：

- `set-mode SEMIAUTOMATIC`
- `operation_mode: SEMIAUTOMATIC`

这些示例说明当前联调习惯是先切到“就绪模式”再发任务，但这不等于协议语义上的最佳归类。

## 4. 字段名称是否有变化

### 4.1 没有变化的部分

对于机器人主动回调上来的消息，当前实现基本是**原样透传**。

例如 `ProtocolGatewayNode` 的 `_publish_payload()` 直接把收到的 JSON 重新 `json.dumps()` 后发到 ROS topic，没有做字段级改名：

- [protocol_gateway_node.py](/home/raybot/raybot_chassis_ws/src/chassis_move/chassis_move/protocol_gateway_node.py:240)

因此，下面这些协议字段名在 `/protocol/*` 中应保持原样：

- `status_msg`
- `mission_msg`
- `map_msg`
- `pose_msg`
- `speed_msg`
- `load_msg`
- `battery_msg`
- `network_msg`
- `mission_state`
- `task_id`
- `task_cmd`
- `task_state`
- `device`
- `code`
- `level`
- `error_msg`
- `error_handling`

### 4.2 有变化的部分

当前代码里主要有 3 类“本地抽象层命名”变化。

#### 1. 本地状态请求字段 `report_duration_sec`，协议字段是 `report_duration`

本地接口：

- `REQUEST_STATUS` 命令里使用 `report_duration_sec`
- `send_status_request()` 的 Python 参数也叫 `report_duration_sec`

但真正发给机器人时，HTTP JSON 字段会被转换成协议要求的：

- `report_duration`

对应代码：

- 本地命名：[protocol_command_bridge.py](/home/raybot/raybot_chassis_ws/src/chassis_move/chassis_move/protocol_command_bridge.py:286)
- 协议落地：[protocol_actions.py](/home/raybot/raybot_chassis_ws/src/chassis_move/chassis_move/protocol_actions.py:51)

结论：

- **这是有意识的本地封装改名**
- 对外协议仍然符合 PDF

#### 2. 本地 ROS topic 名增加了 `/protocol/` 前缀

协议原始 HTTP 地址是：

- `/robot/status`
- `/robot/mission/state`
- `/robot/alarm`

在 ROS 内部被映射为：

- `/protocol/robot_status`
- `/protocol/mission_state`
- `/protocol/robot_alarm`

结论：

- 这是**通道名变化**
- 不是 JSON 字段名变化

#### 3. 当前文档里把 `task_cmd` 简写成了 `cmd`

PDF 中 `TaskStateMessage` 的字段名是：

- `task_cmd`

但当前联调文档里有多处写成：

- `/protocol/task_state` 中出现 `cmd=move`
- `/protocol/task_state` 中出现 `cmd=goto`

相关位置：

- [总控联调验证清单.md](/home/raybot/raybot_chassis_ws/docs/总控联调验证清单.md:116)

结论：

- **协议字段名应以 `task_cmd` 为准**
- 当前代码不会把它改成 `cmd`
- 因此这属于**文档表述不严谨**，不是代码改名

## 5. 状态上报字段与当前代码的实际消费情况

### 5.1 网关层

网关层只做：

- 接收 HTTP 回调
- 转发到 ROS topic

它不解释字段，不做业务判断。

### 5.2 当前真正被消费的状态字段

在当前代码中，最明确被直接读取的状态字段主要是 `pose_msg`：

- `pose_msg.px`
- `pose_msg.py`
- `pose_msg.pt`

对应代码：

- [protocol_teleop_node.py](/home/raybot/raybot_chassis_ws/src/chassis_move/chassis_move/protocol_teleop_node.py:127)

这意味着：

- `lost`
- `lost_reason`
- `stuck`
- `stuck_reason`
- `estop`
- `charging`
- `work_status`
- `score`

这些协议里已经定义的状态字段，**当前工作区并没有专门的业务逻辑去消费或报警**，只是通过 `/protocol/robot_status` 原样提供给上层。

## 6. 与“机器人是否迷路”直接相关的字段

PDF 的 `RobotStatusMessage.status_msg` 中已经明确定义了：

- `lost: boolean` 是否定位丢失
- `lost_reason: string` 定位丢失原因

这说明从协议设计上看，**“机器人是否迷路/定位丢失”最直接的主判据就是 `status_msg.lost`**。

其次可结合：

- `status_msg.stuck`
- `status_msg.estop`
- `status_msg.work_status`
- `/protocol/mission_state`
- `/protocol/task_state`
- `/protocol/robot_alarm`

一起判断。

但当前代码并没有把 `lost` 单独提炼成更高层的 ROS 消息或状态机，因此如果要做“迷路检测”，目前仍需要：

- 订阅 `/protocol/robot_status`
- 读取 `status_msg.lost` 和 `lost_reason`
- 必要时叠加 `mission_state/task_state/alarm`

## 7. 建议

### 7.1 模式建议

如果香橙派当前就是现场上层调度控制器，建议：

- 将“标准工作模式”定义为 `AUTOMATIC`
- 将 `SEMIAUTOMATIC` 仅保留给人工半接管、充电等待、人工辅助恢复等场景

### 7.2 状态上报建议

建议后续补一层更明确的状态消费节点，至少提炼出：

- 是否定位丢失：`status_msg.lost`
- 是否卡住：`status_msg.stuck`
- 是否急停：`status_msg.estop`
- 当前工作状态：`status_msg.work_status`
- 当前任务状态：`mission_state`
- 当前子任务状态：`task_state`

### 7.3 文档建议

建议后续把联调文档中 `/protocol/task_state` 的观察字段：

- 从 `cmd=...`

统一改为：

- `task_cmd=...`

这样才能和协议 PDF 以及当前代码透传结果保持一致。
